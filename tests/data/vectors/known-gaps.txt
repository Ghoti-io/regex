# The vectors this library does not answer the way its oracle does.
#
# One line per record: dialect, flags, pattern, subject, and why.
# Tab-separated; the pattern and the subject are escaped the way the runner
# escapes them, so that a tab or a newline inside one cannot split the line.
#
# This file is a gate in both directions. A vector that fails and is not
# listed here fails the suite; a vector that is listed here and *passes* fails
# it too, with "remove the entry" - so the list can only shrink by somebody
# noticing, and never grows by accident.
#
# The rates the README publishes are the rates without these: a known gap is
# counted and named, never counted as a pass.
#
# Regenerating: run testVectors, which prints the line to add beneath every
# failure it does not recognise. The *reason* is written by hand. A reason
# that begins "not yet classified" is one nobody has looked at, and is meant
# to be read as the admission it is.
perl		(((aa){2})+)	aaaaaaaaaa	a capture a *failed* attempt left behind. Perl reports group 3 of `(((aa){2})+)` against ten a's as 8-10, which is where a third iteration of the outer `+` put it before failing on the second `(aa)`; this library undoes the write when the attempt is abandoned, and reports 6-8, the last iteration that actually ran. Both engines here agree with each other, so this is one answer against the oracle's and not an engine defect. The same question as the four negative-lookahead rows: what the last write *was* when the path that made it was thrown away, which is a fact about where perl's own engine restores an offset rather than a rule a second engine can follow

perl		(?|(?<a>a)|(?<b>b))(?(<a>)x|y)\\1	bxb 	`(?(<a>)` where a branch reset gave two names the same number. Perl 5.40.1 answers as though the name picked out the *definition*: with the `b` branch matched it takes the false arm, and this library resolves the name to the number and takes the true one. Left alone deliberately, because the oracle is not trustworthy here. The numeric form of the same question contradicts perl's own capture report - `(?|(a)|(b))` against "b" reports group 1 as "b", and `(?|(a)|(b))(?(1)x|y)` then matches "by" and not "bx" - and pcre2test 10.46 takes "bx", which is what this library does. That is Perl/perl5#24577, a branch reset regression introduced in 5.38 and closed 2026-07-22, so it is in 5.40.1 and not in whatever comes after 5.44. pcre2test refuses the named pattern outright (error 165: different names for subpatterns of the same number). Re-check both rows when tools/corpus/VERSIONS moves the pin; if the named answer survives a fixed perl it is a rule worth implementing, and if it does not there was never anything here

perl		X(?!b+(?!(c+)*(?!(c+)*d))).*X	aXbbbbbbbcccccccccccccaaaX	the capture state a *repeat* inside a negative lookahead leaves behind. Which captures survive a negative lookaround at all is settled - documentation/dialects.md section 5.17, probed three ways: Perl keeps what the body wrote before failing, pcre2test and Node discard it, and this library follows the dialect. What is not settled is what the last write *was* when the body's failing part is a loop. Perl reports group 2 of `(?!(aa){2}$)` against "aaa" as 0-2 and group 1 of `(?!(aa)*$)` against the same subject as unset, so the counted form keeps its last successful iteration and the starred form does not - which is a fact about where Perl's own engine restores an offset, not a rule a second engine can follow. Reproducing it means reproducing regexec.c

gnu-bre		\\(ab*\\)[ab]*\\1	ababaaa	the overall match is leftmost-*first* and POSIX wants leftmost-longest. glibc reports the whole of "ababaaa"; this library reports the first four characters, which is the match a Perl-family engine finds. That is documentation/plan.md's WP-24 - the Pike VM's longest mode, and a bounded exhaustive mode in the backtracker for the backreference this pattern has - and it is the one thing left that changes an *extent* rather than a subexpression. The profile already says GRX_PREFER_LEFTMOST_LONGEST; no engine reads it yet
gnu-ere		a(b|c?)+d	abcd	POSIX subexpression disambiguation. The overall match agrees with glibc; which iteration of the repeat each group ends up holding does not. POSIX says every subexpression takes the longest match consistent with the whole, and doing that needs the tagged-transition machinery documentation/plan.md's WP-26 names - Okui-Suzuki or Laurikari - which that package schedules after M4 and calls L. This library reports the last iteration that ran, which is what a leftmost-first engine reports and is what every other dialect here wants.
